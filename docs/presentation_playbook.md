## 1. Canva Shared Design System (The "Team Glue")

To make sure 4 separately designed Canva decks look like a unified, professional team presentation, all teammates should stick to these shared visual guardrails:

### Color Palette (Hex Codes)
These colors match the headless Matplotlib charts generated by `src/plots.py`:
* **Midnight Navy (`#1B2A4A`)**: Primary slide headings, title cards, and key text.
* **Slate Blue (`#3979A6`)**: Subheadings, borders, primary bar elements, and card highlights.
* **Alert Brick Red (`#BF4545`)**: Critical warnings, overdue status callouts, and security risk indicators.
* **Warning Amber (`#DD982D`)**: "Due Soon" status tags and data limitation alerts.
* **Success Forest Green (`#438B69`)**: Passing tests, validated date math, and clean data badges.
* **Canvas Background (`#F6F8FB` or pure `#FFFFFF`)**: Light, crisp background (avoids muddy dark-mode contrast issues on classroom projectors).

### Canva Font Pairings
* **Headings**: *Montserrat*, *Inter*, or *Poppins* (Bold, 32–40 pt).
* **Body Text**: *Open Sans*, *Roboto*, or *Lato* (Regular/Medium, 16–20 pt).
* **Code / CLI Snippets**: *Source Code Pro*, *Consolas*, or *JetBrains Mono* (Regular, Monospace, 14–18 pt in a rounded container).

### Reusable Canva Visual Patterns
* **The "Stat Badge"**: A large bold number (e.g. `1,748 Records`, `47 Tests Passed`, `30-Sample Seed 42`) with a small explanatory label below.
* **The "Split Card"**: Left side shows the problem/code snippet, right side shows the defensive solution/result.

### PART 2: Catalog Ingestion, OOP Modeling & Date Arithmetic
**Speaker 2** (~2:30 minutes)  
*Focus: Demonstrating foundational Python programming—JSON parsing, tolerant error handling, OOP class design, and date calculations.*

#### Slide 4: Data Ingestion & Tolerant Parsing
* **Slide Title**: Tolerant Ingestion: Handling "Dirty" Data
* **Visual Elements**:
  - Flowchart: `Raw JSON Snapshot` $\to$ `JSON Parser & Field Validator` $\to$ `Structured Records`.
  - Code highlight box showing safe extraction:
    ```python
    # Safe field extraction with fallback
    cve_id = item.get("cveID")
    date_added = parse_iso_date(item.get("dateAdded"))
    ```
  - Key bullet points:
    - Tolerant parsing: Bad fields become `None` instead of crashing the program.
    - Preservation: Malformed rows and duplicate CVEs are flagged and retained for full audit transparency.
* **What to Say (Speaker Notes)**:
  > "Real-world data is rarely clean. When parsing the KEV JSON snapshot, our first priority was building a tolerant parser. Instead of letting missing dates or malformed rows crash the entire program with an unhandled exception, our parser validates all required fields, converts malformed entries into `None`, and flags them in a diagnostic report while keeping the rest of the catalog intact."

#### Slide 5: The Object-Oriented Model: `VulnerabilityRecord`
* **Slide Title**: Object-Oriented Design: `VulnerabilityRecord`
* **Visual Elements**:
  - Class diagram / Structure card for `VulnerabilityRecord`:
    - **Attributes**: `cve_id`, `vendor_project`, `product`, `date_added`, `due_date`, `known_ransomware_campaign_use`
    - **Methods**: `days_until_due(reference_date)`, `age_days(reference_date)`, `status_at(reference_date)`
  - Callout: *Why OOP? Encapsulation keeps business logic with the data, preventing duplicate date calculations across the app.*
* **What to Say (Speaker Notes)**:
  > "Rather than passing raw dictionaries through every function, we modeled each vulnerability as an Object-Oriented `VulnerabilityRecord` class. This gives us clear encapsulation: the record holds its own attributes, and methods like `days_until_due()` and `status_at()` calculate deadline logic directly on the object. This makes our code modular, testable, and clean."

#### Slide 6: Date Arithmetic & The 4 Deadline States
* **Slide Title**: Deadline Statuses & Boundary Logic
* **Visual Elements**:
  - Timeline graphic showing a `Reference Date` and the 4 status buckets:
    - **Overdue (`< 0 days`)**: Past CISA's required action date [Red].
    - **Due Soon (`0 to 14 days`)**: Immediate remediation window [Amber].
    - **Not Yet Due (`> 14 days`)**: Future deadline [Green].
    - **No Due Date (`None`)**: Handled gracefully without errors [Gray].
  - Callout note: *Handling edge cases: leap years, negative age guards, and reproducible frozen reference dates.*
* **What to Say (Speaker Notes)**:
  > "Date arithmetic can be tricky. We calculate both the age since catalog addition and the time remaining until CISA's required remediation date relative to a configurable reference date. As shown on the timeline, vulnerabilities fall into four distinct categories: Overdue, Due Soon within 14 days, Not Yet Due, or No Due Date. We specifically tested leap years and boundary cases—for example, a vulnerability due today has zero days remaining and is classified as 'Due Soon', not 'Overdue'. Next, [Speaker 3] will show how our dashboard filters, prioritizes, and visualizes this data."

## 4. Professor & Peer Q&A Cheat Sheet

Prepare your team with these crisp, confident answers to likely questions:

### Q1: "Why did you use an Object-Oriented class (`VulnerabilityRecord`) instead of just keeping raw Python dictionaries?"
* **Answer**:  
  *"While dictionaries are convenient, an OOP class gives us encapsulation and type safety. By putting methods like `days_until_due()` and `status_at()` inside `VulnerabilityRecord`, our date calculation logic is defined in exactly one place. If the policy for 'Due Soon' ever changes, we update one method rather than editing dictionary operations across multiple files."*

### Q2: "Why didn't you calculate a CVSS score or an overall risk score?"
* **Answer**:  
  *"The CISA KEV catalog intentionally does not provide CVSS numeric scores, and both the project specification and defensive security best practices advise against inventing arbitrary formulas. An invented severity formula gives a false sense of precision. Instead, our prioritization is completely transparent, auditable, and based on regulatory remediation deadlines."*

### Q3: "What happens if a record in the catalog has a missing or invalid due date?"
* **Answer**:  
  *"Our tolerant parser sets `due_date` to `None` and records a data-quality flag in our diagnostic report. In our prioritization sorting, records without due dates are never discarded; they are placed safely at the end of the worklist so security teams can manually investigate them without losing visibility."*

### Q4: "Why do you emphasize that vendor counts do not equal risk?"
* **Answer**:  
  *"If an analyst only looks at raw counts, they might conclude that Microsoft or Cisco is insecure because they have the most KEV entries. In reality, large enterprise vendors have massive codebases, millions of deployments, and active vulnerability disclosure programs. High counts reflect software ubiquity and active discovery, not poor security posture."*

### Q5: "How does your 30-record sample verification work?"
* **Answer**:  
  *"We used Python's `random.seed(42)` to deterministically sample 30 rows from the frozen dataset. Then, our verification module calculates each record's age and due offset using calendar ordinal math completely independent of the model's timedelta logic, exporting a markdown verification table for human review."*
